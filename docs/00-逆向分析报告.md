## 2. 加固结论：代码是加密的，静态改不了 smali

`classes.dex` 头部（71,061,232 字节）：

| 字段 | 值 | 说明 |
|---|---|---|
| class_defs_size | **30** | 整个 71MB dex 里只有 30 个类 |
| method_ids_size | **656** | 只有 656 个方法 |
| string_ids_size | 1061 | 字符串极少 |

apktool 解包结果：**30 个 smali 文件、约 0.4 MB**，全部是壳：

```
com/netease/nis/wrapper/MyApplication.smali      ← 应用入口
com/netease/nis/wrapper/MyJni.smali              ← 调用 libnesec.so
com/netease/nis/wrapper/NEDialog.smali           ← 检测失败弹窗
com/netease/nis/wrapper/plugin/InstrumentationProxy.smali  ← 拦截生命周期
com/netease/nis/wrapper/plugin/a..g.smali        ← 运行时解密并加载真 dex
```

也就是说：**真正的业务代码和广告代码全部被加密在那 71MB 里，运行时由网易易盾壳解密后动态加载**。
除壳之外确认的保护：

| 保护 | 证据 |
|---|---|
| 网易易盾（加固） | `com.netease.nis.wrapper.*`、`VER="7.6.1_817"`、`libnesec.so` |
| 爱加密（部分原生库） | `libijiami_1011.so` |
| 腾讯天御 | `libsecsdk_tianmu.so` |
| 反调试 / 反虚拟机 | APKiD：`Debug.isDebuggerConnected()`、Build.* 系列检测、`ro.kernel.qemu`、模拟器文件检测 |
| Flutter | `libflutter.so`、`assets/flutter_assets`（主 UI 是 Flutter） |

**因此：改 smali → 重打包这条路走不通**（没有可改的 smali）；即使脱壳后重打包，
重签名也大概率触发壳/业务层的完整性校验，而且本机 x86_64 模拟器没有 ARM 转译、跑不起来这个包。

## 4. 关键突破口：官方自己给广告域名单独开了「证书豁免」

`res/xml/network_security_config.xml` 原文（含开发者自己的中文注释）：

```xml
<base-config cleartextTrafficPermitted="true">
    <trust-anchors><certificates src="system" /></trust-anchors>   <!-- 业务域名：只信系统证书 -->
</base-config>
<domain-config cleartextTrafficPermitted="true">
    <domain includeSubdomains="true">i.snssdk.com</domain>
    <domain includeSubdomains="true">is.snssdk.com</domain>
    <domain includeSubdomains="true">pangolin.snssdk.com</domain>
    <domain includeSubdomains="true">extlog.snssdk.com</domain>
    <domain includeSubdomains="true">sf3-ttcdn-tos.pstatp.com</domain>
    <domain includeSubdomains="true">bds.snssdk.com</domain>
    <domain includeSubdomains="true">dig.bdurl.net</domain>
    <domain includeSubdomains="true">mi.gdt.qq.com</domain>
    <domain includeSubdomains="true">v2mi.gdt.qq.com</domain>
    <domain includeSubdomains="true">v3mi.gdt.qq.com</domain>
    <trust-anchors>
        <certificates src="user" /> <!-- 信任用户自己安装的证书 -->
        <certificates src="system" />
    </trust-anchors>
</domain-config>
```

这 10 个域名分属穿山甲（6 个）、优量汇（3 个）、百度（1 个），**全是广告域名**；
而 App 自己的业务接口（实测为 `*.gxapp.iydsj.com`）走的是 `base-config`，只信系统证书。
换句话说：**广告流量和业务流量在域名层面完全分离**，拦广告不会影响跑步、打卡、成绩等业务。

## 6. 为什么最终交付「规则」而不是「改好的 APK」

| 路线 | 可行性 | 原因 |
|---|---|---|
| 改 smali 重打包 | ❌ | 代码被易盾加密，30 个壳类之外没有可改的代码 |
| 脱壳后重打包 | ⚠️ 需真机 | 需 ARM 真机运行 App 后用 Frida dump dex；本机只有 x86_64 模拟器，**模拟器不支持跨架构 ARM 镜像**（已实测报错） |
| LSPosed 模块 | ⚠️ 需真机测试 | 需要真机装模块逐个试 hook；没有设备无法验证，盲发模块有把 App 搞崩的风险 |
| **域名拦截** | ✅ **立即可用** | 广告 SDK 全部依赖这些域名；改 DNS/规则即可，不动 APK、不触发加固校验、不需要重签名 |

所以交付物是**按这个 App 实测数据整理的域名拦截规则**，见 `rules/` 目录。

### 安全版 vs 完整版

- **安全版（推荐）**：只保留**广告专用域名**（如 `gdt.qq.com`、`pangolin-sdk-toutiao.com`、`sdk.e.qq.com`…），
  排除了 `taobao.com`、`snssdk.com`、`pstatp.com`、`kuaishou.com`、`alicdn.com` 这类
  **大厂主域/公共 CDN**，全局拦截不会误伤淘宝、抖音、快手等其它 App。
- **完整版**：包含 128 条全部域名，拦截更彻底，但其中 31 条是父域/CDN，
  **只建议配合「按 App 生效」的过滤器（AdGuard for Android 的按应用过滤）使用**，不要直接全网络生效。

## 8. 局限性（务必知道）

1. **广告位可能留白**：请求被拦后，部分广告容器会显示空白/占位，不影响 App 功能。
2. **极少数情况会漏**：如果 SDK 使用 DoH 或硬编码 IP，域名拦截无效（本项目实测的主流 SDK 不走）。
3. **OTS 推广/弹窗**：`com.acse.ottn.*` 的弹窗和拉活走另一批域名，安全版已包含；
   若仍有残留，把完整版加上或等后续 LSPosed 方案。
4. **完整版全局生效的误伤**：见上，务必按需选择。

## 9. 如果一定要「改好的 APK」

需要一台 **root 的 ARM 手机**（你机器上有 LSPosed / ReZygisk 安装包，大概率具备）：

1. 手机开「无线调试」，用 `adb pair` / `adb connect` 连到我这个 WSL 里；
2. 我推 `frida-server`（arm64，已备好 17.24.3），用 `frida-dexdump` 把易盾解密后的真实 dex 全量 dump 出来；
3. 反编译定位广告初始化/展示逻辑，改代码 → 重新打包 → 签名；
4. 真机验证（易盾/爱加密可能有签名校验，需要额外处理，成功率不是 100%）。

或者更稳的路线：**按你这个版本写一个 LSPosed 模块**，直接 hook 掉
`mvi.splash.AdActivity` 等广告页和广告 SDK 的加载调用，不改原 APK、不触发签名校验。
两条路都需要把手机连上来实测。
